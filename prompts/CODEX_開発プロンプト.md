# 予定表Webアプリケーション 開発プロンプト

## 1. Codexへの依頼

このリポジトリに、ユーザー・会議室・備品の予定を管理する、シンプルなタイムライン型予定表Webアプリケーションを設計・実装してください。

本書をプロダクト要求と実装方針の基準とします。まずリポジトリ内の `AGENTS.md`、既存コード、設定、参照画像を確認し、既存資産があれば尊重してください。要求の矛盾や実装を左右する重大な不明点だけを質問し、それ以外は本書の暫定方針に従って進めてください。

いきなり全機能を一括実装せず、最初に短い実装計画と採用技術を提示し、その後、動作確認可能な小さな単位で実装してください。各段階で関連するテスト、静的解析、ビルドを実行し、結果と残課題を報告してください。

### 作業権限

- 読み取り、リポジトリ内の編集、依存関係の追加、Dockerイメージのビルド、テスト実行など、通常のローカル開発作業は進めてよい。
- データ削除、既存コードの大規模な破壊的変更、外部サービスへのデプロイ、課金を伴う操作、秘密情報の生成・登録は事前に確認すること。
- 認証情報や秘密鍵をコミットしないこと。

## 2. プロダクト概要

「kobareo-calendar」や Outlook の予定表に近い操作感を持ちながら、メールやオンライン会議機能を除外し、予定管理に特化したWebアプリケーションを作成します。

主な利用者は次の2種類です。

- 一般ユーザー: 自分や閲覧対象ユーザー、会議室、備品の予定を閲覧・登録する。
- 管理者: 一般ユーザーの機能に加えて、ユーザーを管理する。

## 3. MVPの機能範囲

### 3.1 認証・認可

- メールアドレスをログインIDとして、パスワードでログインできること。
- ログアウトできること。
- ユーザーのロールは `Admin` と `User` の2種類とすること。
- 未認証ユーザーはログイン画面以外へアクセスできないこと。
- ユーザー管理画面、ユーザー管理ボタン、ユーザー管理APIは管理者だけが利用できること。フロントエンドで隠すだけでなく、APIでも必ず認可すること。
- パスワードは平文保存せず、ASP.NET Core Identityなど実績のある仕組みを使って安全にハッシュ化すること。
- 認証トークンを `localStorage` に永続保存しないこと。採用する認証方式、Cookie属性、CSRF対策、CORS設定を設計書に記載すること。
- 初期管理者の作成方法を用意し、認証情報は環境変数または開発専用シードで注入すること。

### 3.2 ユーザー管理（管理者のみ）

- ユーザー一覧、検索、追加、編集、無効化を行えること。
- 管理項目は、表示名、メールアドレス、ロール、有効・無効とすること。
- メールアドレスは大文字・小文字を考慮して一意にすること。
- 物理削除は原則行わず、過去予定との整合性を保つため無効化を採用すること。
- 自分自身を無効化する操作、および有効な管理者が0人になる操作を防止すること。
- パスワード再設定方法を用意すること。MVPでは管理者による仮パスワード設定でもよいが、本番運用上の注意を文書化すること。

### 3.3 予定の登録・編集・削除

予定は次の情報を持つこと。

- 開始日時
- 終了日時（開始日時より後であること）
- 予定の題名
- 予定の詳細
- 非公開フラグ
- 作成者
- 予定の対象者（自分および他のユーザーを複数選択可能）
- 予約対象リソース（会議室・備品を複数選択可能）
- 作成日時、更新日時

予定の登録、詳細表示、編集、削除ができること。通常、編集・削除できるのは予定の作成者と管理者だけとします。対象者に追加されたユーザーは閲覧のみ可能とする暫定方針です。

「他のユーザーの予定に追記する」は、1件の予定に複数ユーザーを対象者として追加し、それぞれのタイムラインに同じ予定を表示する機能として実装してください。ユーザーごとに予定のコピーを作らず、単一の予定と参加対象の関連で表現してください。

### 3.4 重複予定

- 選択したユーザー、会議室、備品のいずれかに同一時間帯の既存予定がある場合、登録・更新前に競合を検出すること。
- 境界が接するだけの予定（例: 10:00終了と10:00開始）は重複としないこと。
- 重複がある場合は「選択した対象には、同じ時間帯に別の予定があります。それでも登録しますか？」という趣旨の警告を表示し、競合対象を一覧表示すること。
- ユーザーが明示的に続行した場合は登録できること。重複を禁止しないこと。
- APIは通常の登録要求と、競合確認後の明示的な登録要求を区別し、画面側だけで警告を回避できない設計にすること。
- 同時登録による競合も考慮し、競合確認から登録までの整合性方針を説明すること。

### 3.5 非公開予定

- 非公開予定の題名と詳細は、作成者、対象者本人、管理者以外には表示しないこと。
- 権限のない閲覧者には時間帯と「非公開の予定」であることだけを表示すること。
- APIレスポンスの段階で秘匿し、フロントエンドへ題名・詳細を送らないこと。
- 会議室・備品のタイムライン経由で閲覧した場合も同じルールを適用すること。

### 3.6 会議室・備品

- 予定の対象として `Room`（会議室）と `Equipment`（備品）を扱えること。
- リソースは名称、種類、有効・無効を持つこと。
- MVPでは管理者がリソースを一覧、追加、編集、無効化できる管理画面も実装すること。
- 無効なリソースには新規登録できないが、過去予定は表示可能とすること。

## 4. 予定表UI（最重要）

参照画像:

`/home/kbr109/src/personal/apps/kobareo-calendarコピープロジェクト/prompts/スケジュール表UI.png`

画像の基本構造を参考にし、単なる月間カレンダーではなく、左側に表示対象、右側に時刻軸を配置する日単位のタイムライン表を実装してください。画像をそのまま複製するのではなく、実用性、アクセシビリティ、レスポンシブ表示を補ってください。

### 4.1 基本表示

- ログイン直後は今日の日表示とし、自分のタイムラインだけを表示すること。
- 左端に表示対象の名称、右側に時刻グリッドを表示すること。
- 前日、翌日、今日への移動と日付選択ができること。
- 表示時間帯の暫定値は 08:00〜20:00、最小表示単位は30分とすること。ただし設定値として変更しやすくすること。
- 横方向に時刻、縦方向にユーザー・会議室・備品を並べること。
- 対象名列と時刻ヘッダーはスクロール時に追従すること。
- 現在時刻線を表示すること。
- 予定ブロックには、表示可能な範囲で題名と開始・終了時刻を表示し、選択すると詳細を開くこと。
- 空き時間を選択して、新規予定フォームを開始できること。ドラッグ操作を採用する場合も、キーボードやフォーム入力による代替手段を必ず用意すること。

### 4.2 表示対象の追加・削除

- 自分は常にデフォルト表示すること。
- ユーザー一覧を検索・チェック選択し、他ユーザーのタイムラインを追加・削除できること。
- 会議室・備品も種類別に検索・チェック選択できること。
- 選択状態はユーザーごとの表示設定として保存し、次回ログイン時にも復元すること。
- 自分自身は一覧から外せないこと。

### 4.3 重複予定の描画

- 同じ表示対象で時間が重複する予定は、互いに隠れないよう同一行内の別レーン（2段目、3段目）へ積み上げること。
- 区間分割またはinterval partitioningにより、同時刻に重ならない予定は同じレーンを再利用すること。
- レーン数に応じて対象行の高さを拡張すること。
- 重複予定は色、枠線、アイコン等でも判別しやすくすること。色だけに意味を依存させないこと。
- 予定色は安定した規則で決めること。MVPでは作成者または予定ID由来の色でよい。

### 4.4 UI品質

- シンプルで業務利用しやすいデザインとし、過剰な装飾を避けること。
- デスクトップを主対象とするが、狭い画面では横スクロール等により操作不能にならないこと。
- キーボード操作、フォーカス表示、フォームラベル、十分なコントラスト、ARIA属性を考慮すること。
- ローディング、データなし、APIエラー、権限エラーを明確に表示すること。
- 削除など不可逆な操作には確認ダイアログを表示すること。

## 5. 推奨技術スタック

タイムライン配置、複雑なフォーム状態、認証状態、API通信、テストの保守性を考慮し、フロントエンドには JavaScript フレームワークの利用を推奨します。

### フロントエンド

- React + TypeScript + Vite
- HTML5 / CSS（既製UIライブラリを使う場合もタイムライン本体は要件に合わせて実装）
- API通信・サーバー状態管理は TanStack Query 等を検討
- フォームとバリデーションは React Hook Form + Zod 等を検討
- テストは Vitest + Testing Library、主要操作のE2Eは Playwright を検討
- 依存ライブラリは必要最小限とし、選定理由をREADMEへ記載

### バックエンド

- サポート中の .NET LTS版 / ASP.NET Core Web API / C#
- Clean Architectureを採用し、少なくとも Domain、Application、Infrastructure、WebApp の責務を分離
- Entity Framework Core
- ASP.NET Core Identity または同等の標準的な認証基盤
- OpenAPI仕様を生成し、フロントエンドとの契約を明確化
- 入力検証、統一的なProblem Details形式のエラーレスポンス、構造化ログを実装

Clean Architectureは層を増やすこと自体を目的にせず、依存関係を内側へ向け、業務ルールをWeb APIやEF Coreから分離してください。

### データベース

- 開発環境: SQLite
- 本番環境: SQL Server
- EF CoreのDBプロバイダーを設定で切り替え可能にすること。
- SQLiteとSQL Serverの両方で動作するLINQ・型・マイグレーションを使用し、プロバイダー固有SQLへの依存を避けること。
- 日時はDBおよびAPIではUTCで保持・交換し、画面では利用者のタイムゾーンへ変換すること。MVPの既定タイムゾーンは `Asia/Tokyo` とすること。
- 本番用SQL Serverをローカル開発の必須条件にしないこと。ただしSQL Server互換性をCIまたは任意のComposeプロファイルで検証できる構成を検討すること。

### 実行・インフラ

- 開発環境は `docker compose up --build` でフロントエンドとバックエンドを起動できること。
- 開発用SQLiteデータは名前付きボリュームへ保存すること。
- フロントエンドとバックエンドはそれぞれ本番用Dockerfileを持つこと。
- 本番はGoogle Cloud Runへ別サービスとして配置できる、ステートレスなコンテナ構成にすること。
- Cloud Runではローカルファイルを永続DBとして使わず、SQL Serverへの外部接続を環境変数で設定すること。
- コンテナはCloud Runが渡す `PORT` を尊重し、非rootユーザー、ヘルスチェック、標準出力ログ、graceful shutdownを考慮すること。
- 設定値は環境変数へ外出しし、開発用サンプルは `.env.example` に秘密情報なしで記載すること。

## 6. ドメインモデルの最低要件

実装前にER図または同等のデータモデルを提示してください。少なくとも次の概念を含めます。

- `User`: 認証情報、表示名、ロール、有効状態
- `Schedule`: 題名、詳細、開始・終了UTC、非公開フラグ、作成者、監査項目
- `ScheduleParticipant`: 予定と対象ユーザーの多対多関連
- `Resource`: 会議室または備品、名称、種類、有効状態
- `ScheduleResource`: 予定とリソースの多対多関連
- `UserTimelinePreference`: ユーザーごとの表示対象と並び順

削除済み・無効化済みのユーザーやリソースを過去予定から参照できるよう、外部キーと削除方針を明示してください。更新競合に備えて楽観的排他制御も検討してください。

## 7. APIの最低要件

REST APIとして、少なくとも次のユースケースを提供してください。具体的なURIとDTOは実装前に整理してください。

- ログイン、ログアウト、現在のログインユーザー取得
- 指定日時範囲・表示対象の予定一覧取得
- 予定詳細取得、作成、更新、削除
- 登録・更新時の競合検出と、警告を承認した確定操作
- 選択可能なユーザー、会議室、備品の検索・一覧取得
- 自分のタイムライン表示設定の取得・更新
- 管理者によるユーザー管理
- 管理者による会議室・備品管理

一覧APIは不要な個人情報を返さず、非公開予定の秘匿処理を必ずサーバー側で行ってください。日時範囲には上限を設け、将来のデータ増加に耐えるインデックスを設計してください。

## 8. セキュリティ・品質要件

- OWASPの一般的なWebセキュリティ対策を適用すること。
- 認証・認可、IDOR、XSS、CSRF、SQLインジェクション、ブルートフォース、過剰なエラー情報に注意すること。
- ログイン試行回数制限またはロックアウトを設けること。
- HTMLとして予定の題名・詳細を直接描画しないこと。
- APIの全更新系処理で認証・認可・入力検証を行うこと。
- 個人情報、パスワード、認証トークン、非公開予定の内容をログへ出さないこと。
- DBマイグレーション手順、バックアップ・復元方針、本番での秘密情報管理方針をREADMEへ記載すること。

## 9. テスト要件

最低限、次を自動テストしてください。

- 開始・終了日時の検証と、予定重複判定（境界値を含む）
- 重複しても明示承認後は登録できること
- 非公開予定が権限のないAPI利用者へ漏れないこと
- 一般ユーザーが管理APIを利用できないこと
- 作成者以外が予定を更新・削除できないこと
- 無効ユーザー・無効リソースへ新規予定を登録できないこと
- タイムラインのレーン割り当てで、重複ブロックが同じレーンに置かれないこと
- ログインから予定作成、競合警告、表示、編集、削除までの主要E2Eフロー
- 管理者のユーザー管理フロー

バックエンドの業務ルールはユニットテスト、DBや認証を含む処理は統合テスト、ユーザーの主要操作はE2Eテストで検証してください。

## 11. 完了条件

- `docker compose up --build` により開発環境が起動する。
- 初期管理者と一般ユーザーでログインでき、ロールごとの画面・API権限が正しい。
- ユーザー、会議室、備品を対象に予定を登録できる。
- 非公開予定が権限に応じて正しく秘匿される。
- 競合が警告され、承認すれば重複登録できる。
- 重複予定がタイムライン上で別レーンに表示され、互いに隠れない。
- 表示対象の追加・削除と設定保存ができる。
- 管理者だけがユーザーとリソースを管理できる。
- 主要テスト、ビルド、静的解析が成功する。
- READMEにセットアップ、アーキテクチャ、設定、DB切替、マイグレーション、テスト、Cloud Runデプロイ前提、既知の制約が記載されている。

## 12. 暫定方針と要確認事項

以下は元の要求だけでは確定できないため、MVPの暫定方針です。実装開始時にユーザーへ一覧で提示し、変更希望がなければこの方針で進めてください。

1. 他ユーザーを予定へ追加しても、そのユーザーによる承認・辞退は不要とする。
2. 予定の編集・削除は作成者と管理者のみ可能とする。
3. 非公開予定は作成者、対象者本人、管理者には全文を表示する。
4. 会議室・備品の重複予約は禁止せず、ユーザー予定と同様に警告後の登録を許可する。
5. 繰り返し予定、終日予定、通知、メール送信、添付ファイル、外部カレンダー同期、監査ログ、多言語対応はMVP対象外とする。
6. 1件の予定は日をまたいで登録可能とし、日表示では表示範囲に合わせて分割描画する。
7. 既定タイムゾーンは `Asia/Tokyo` とし、夏時間を含む他地域対応を妨げないデータ設計にする。
8. ユーザーが閲覧できる他ユーザーの範囲は、MVPでは同一システム内の有効ユーザー全員とする。

実運用前には、組織・部署単位の閲覧制限、管理者による監査、予定変更履歴、通知、リソースの重複禁止ルール、パスワード再設定メール、データ保持期間、個人情報保護、可用性目標、バックアップ目標（RPO/RTO）を追加検討してください。

## 13. Codexの報告形式

各フェーズの完了時は、次の順に簡潔に報告してください。

1. 完了した内容
2. 主要な設計判断と理由
3. 変更ファイル
4. 実行した検証と結果
5. 未完了事項、既知の制約、次の作業

実装が要求を満たしたと言う場合は、対応するテスト結果または再現手順を添えてください。
